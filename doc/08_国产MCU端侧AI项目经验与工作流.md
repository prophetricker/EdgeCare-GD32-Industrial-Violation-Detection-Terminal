# 国产 MCU 端侧 AI 项目经验与工作流

更新日期：2026-06-20

本文总结 EdgeCare 项目中可复用的方法。目标不是复盘细节，而是沉淀一套下次做国产芯片、传感器接入、端侧 AI 演示项目时可以直接套用的工作流。

## 1. 总原则

1. 先跑通最短闭环，再追求完整功能。
   - 嵌入式项目最容易卡在“同时怀疑供电、烧录、串口、外设、算法”。第一版必须先做到上电、串口、单个 GPIO、单个传感器、单帧数据、单次推理、单次报警逐层可证。

2. 控制面和数据面分开验证。
   - 摄像头能读到 SCCB ID，只证明控制面可用，不证明 DVP/DCI/DMA 数据面可用。
   - 雷达 OUT 会变化，只证明触发源可用，不证明报警策略正确。
   - 模型离线准确率高，只证明训练脚本当前数据上可用，不证明上板输入分布一致。

3. 每次只改一个变量。
   - 对寄存器、引脚、采样边沿、DMA、模型阈值、数据集都采用单变量 A/B。每个实验记录“改了什么、怎么验证、结论是什么、是否作为默认”。

4. 已验证的可用版本必须优先保存。
   - 在做高风险排查前先提交或打 tag。可拍数据、可演示、可烧录的版本比“理论上更正确但未验证”的版本重要。

5. 模型输入以 MCU 实际看到的数据为准。
   - 不追求先采漂亮彩色照片。训练数据应直接来自固件最终推理入口，例如本项目的 `96x96 gray8`，这样数据分布和上板运行一致。

## 2. 推荐项目骨架

一个新的国产 MCU 端侧 AI 项目，建议一开始就建立这些文件：

- `AGENTS.md`
  - 写清楚板卡、主控、目标、关键引脚、构建命令、串口参数、禁止自动做的事。

- `CODING_STYLE.md`
  - 写清楚模块边界、命名规则、日志格式、DMA/缓存规则、禁止动态分配等嵌入式约束。

- `看板.md`
  - 只放当前真实状态：当前可演示能力、阻塞项、下一步、已验证命令、Git 状态、禁止提交清单。

- `doc/00_先看这里_文档索引.md`
  - 把文档分层，避免资料越堆越乱。

- `doc/01_数据集采集全流程手册.md`
  - 采集固件配置、串口命令、目录结构、类别定义、质检步骤、重训步骤。

- `doc/02_硬件引脚与接线说明.md` 和 `doc/03_快速接线表.md`
  - 所有实物接线都在这里更新。不要只靠聊天记录记忆。

- `doc/04_外设调试记录.md`
  - 记录传感器 bring-up 过程，例如 ID、寄存器、时序、失败实验和保留原因。

- `tools/verify_project.ps1`
  - 汇总单测、静态检查、构建检查、安全扫描。提交前只跑一个命令即可复核。

- 项目级 skill
  - 当板卡、引脚、日志、构建路径稳定后，把这些事实写进项目 skill。新会话就不会反复忘记“串口是哪个、报警低有效、Keil target 叫什么”。

## 3. 分层 Bring-up 流程

推荐顺序如下。

### 3.1 电源与下载链路

先确认：

- 板卡 3V3/GND 电压稳定。
- 调试器 VTref 稳定，不随手触 USB 或排线大幅波动。
- SWDIO/SWCLK/GND/VTref/NRST 接线可被工具识别。
- 有一个已知可用的烧录方式，例如 GD-Link 或 J-Link。不要同时赌两个不稳定工具链。

经验：

- 烧录器问题和固件问题要分开。若全新板、空工程、官方 demo 都无法连接，优先查供电、驱动、接线、调试器，不要先改应用代码。
- 比赛时间紧时，选“当前稳定烧录链路”，不要消耗大量时间追求理论上更通用的烧录器。

### 3.2 串口优先

第一版固件只做：

```text
boot...
[ts_ms] state=IDLE seq=N
```

串口稳定后再接其他功能。日志格式要从第一天固定，后续脚本才能长期复用。

经验：

- 启动日志只打印一次，周期日志持续打印。
- 周期日志字段名不要随意变更。
- 大块图像数据不要混进周期日志，图像 dump 应有明确 `begin/end/checksum`。

### 3.3 GPIO 和低风险外设

先接报警灯、雷达 OUT、按键这类简单 GPIO：

- 输入输出电平是否符合预期。
- 高有效/低有效是否在文档和代码中一致。
- 周期日志能否直接反映输入和输出状态。

经验：

- 报警类 GPIO 建议封装成 BSP，不要在业务逻辑里到处直接写寄存器。
- 雷达等触发源只做“是否需要视觉判断”的门控，不应直接等价为最终报警。

### 3.4 复杂外设先控制面后数据面

以摄像头为例：

1. 先通电、复位、PWDN。
2. 再读 SCCB/I2C ID。
3. 再配置最小输出格式。
4. 再检查 PCLK/HREF/VSYNC 是否有跳变。
5. 再开 DCI/DMA 抓一帧。
6. 再做像素解释、预处理和模型输入。

经验：

- 控制面成功不能推导数据面成功。
- DCI/DMA 成功不能推导像素解释正确。
- 能看到灰度真实场景，就足以先做端侧 AI MVP；彩色修复可以作为后续增强。

## 4. 数据集与算法闭环

端侧 AI 项目的核心不是一次性训练，而是闭环：

```text
实机场景 -> MCU 原始输入 -> 质检 -> 训练 -> 导出 C 头文件 -> 上板 -> 误报/漏检 -> 补 hard-negative/hard-positive
```

推荐做法：

- 采集 MCU 最终输入，例如 `gray96`，而不是外部相机照片。
- 每个样本文件名包含 label、variant、尺寸、checksum。
- 采完立即运行质检，检查类别数、尺寸、variant、坏帧。
- 每次误报都补同光照、同机位、同画面的 empty/safe hard-negative。
- 每次漏检都补同姿态、同距离、同边界条件的 intrusion hard-positive。
- 不把污染样本直接删除，可以移到 `needs_review/`，避免误用但保留追溯。

模型选择建议：

- 小样本、比赛演示阶段，先用灰度统计、网格统计、HOG + Logistic Regression/SVM 这类可解释模型做 baseline。
- 数据明显变多后，再考虑小 CNN、MobileNet 派生结构、NPU/NN 编译链。
- MCU 上必须有离线回放和固件等价回放，确认 Python 模型与 C/Q15 模型一致。

## 5. 固件架构建议

固件建议分成以下层：

```text
main.c
  只做 cache/systick/board init，然后进入 app loop

app/
  状态机、投票、报警策略、业务日志

bsp/
  传感器、报警灯、串口语音、摄像头、雷达

vision/
  图像预处理、缩放、灰度化、ROI

model/
  固定模型接口、导出的权重、推理结果

platform/
  日志、时间、公共平台封装
```

关键约束：

- `main.c` 不堆业务逻辑。
- DMA buffer 明确对齐，并在 DMA 交接点处理 cache。
- 所有等待必须有 timeout。
- 推理接口固定，不让上层知道模型内部实现。
- placeholder 必须在日志和注释中标明，不能混成真实模型。

## 6. 工具链工作流

推荐保留三类脚本：

- 构建脚本
  - 例如 `build_keil.ps1` 或 skill 封装的 Keil build。

- 烧录脚本
  - 默认不要自动烧录。只有用户明确要求或演示阶段才执行。
  - 不同烧录器分开脚本，例如 GD-Link 和 J-Link 不要混在一个不透明脚本里。

- 串口采集脚本
  - 支持固定 COM、baud、duration、output。
  - 图像 dump、日志抓取、协议发送分开。

提交前检查建议固定为：

```powershell
py -m pytest <关键测试> -q
powershell -ExecutionPolicy Bypass -File .\tools\verify_edgecare.ps1 -SkipSafetyScan
git diff --check
git status --short --ignored
```

上传前必须确认 `.gitignore` 排除：

- `data/`
- `models/`
- Keil `Objects/`、`Listings/`
- `.embeddedskills/logs/`
- PDF、压缩包、SDK、工具链
- DOCX 等生成物，除非比赛提交明确需要

## 7. Skill 和工作流沉淀

本项目有几类经验适合沉淀成 skill 或固定工作流。

### 7.1 通用 embedded skill

适合抽象为通用能力：

- Keil 工程扫描、target 枚举、构建日志解析。
- 串口扫描、抓日志、发送命令、保存文件。
- build -> flash -> observe 的薄编排。

这些能力与具体项目无关，应该复用。

### 7.2 项目级 skill

适合写进项目 skill：

- 当前板卡：`GD32H759I-START`。
- 串口：`COM8 115200 8N1`。
- 报警：`PA8` 低有效。
- 雷达：`PF8` 高有效。
- 相机：OV5640，SCCB、DCI、DMA、当前可用采集路径。
- 模型输入：`96x96 gray8`。
- 默认构建命令、禁止自动烧录、禁止提交文件。

项目级 skill 的价值是降低上下文丢失成本。每次新会话先读 skill，就能直接进入当前事实，而不是重新问一遍接线和构建路径。

### 7.3 项目文档工作流

每次重要变更后同步更新：

1. `看板.md`：当前状态和下一步。
2. 接线变化：`doc/02_硬件引脚与接线说明.md`、`doc/03_快速接线表.md`。
3. 外设根因排查：对应调试记录。
4. 数据集变化：采集手册或数据集报告。
5. 模型变化：训练脚本、指标 JSON、固件模型头文件说明。

不要把文档写成历史流水账。看板保存当前状态，长历史放调试记录。

## 8. 下次项目的推荐节奏

如果下次仍是 10 到 20 天级别的比赛项目，建议这样排：

1. Day 1：Git、看板、串口、最小日志、构建脚本。
2. Day 2：一个输入、一个输出、最小状态机。
3. Day 3-5：核心传感器控制面和数据面。
4. Day 6-7：采集 MCU 实际输入，做第一版 baseline。
5. Day 8-10：上板推理、投票、报警、误报/漏检闭环。
6. Day 11-12：补数据和稳定演示链路。
7. Day 13-14：论文、视频、PPT、GitHub 清理。
8. Day 15：只做低风险修复，不再大改架构。

关键判断：

- 一旦“可用 MVP”出现，先保存、提交、打 tag。
- 不要在比赛末期把主线押在未验证的大模型、复杂联网、彩色图像修复或不稳定烧录器上。
- 演示项目最需要的是可重复运行，而不是每个局部都理论最优。

## 9. EdgeCare 项目可复用结论

EdgeCare 中已经验证出几条对国产 MCU 开发很有价值的经验：

- GD32H759 + OV5640 的 DCI/DMA 采集可以在资料不完整、没有现成 BSP 的情况下通过分层验证跑通；这类工作本质上是在给具体板卡写外设 BSP。
- 对端侧 AI，`gray96` 这类 MCU 真实输入比彩色照片更直接、更稳定、更适合快速形成模型闭环。
- 雷达门控 + 视觉判断 + 多帧投票，比单独雷达或单帧视觉更适合比赛演示。
- 误报和漏检不是一次训练能解决的问题，必须现场采 hard-negative/hard-positive。
- 国产芯片工具链可能存在烧录器、驱动、IDE、OpenOCD/J-Link/GD-Link 兼容性问题；项目要保留一条“已验证可烧录”的主链路。
- `AGENTS.md + CODING_STYLE.md + 看板.md + 文档索引 + verify 脚本 + 项目 skill` 是值得保留的工作资产，下次可以直接复制后按项目修改。
