# 工厂违规检测两人开发流程

更新时间：2026-06-03

## 项目收敛版本

项目名暂定：EdgeCare 面向隐私保护的 GD32H7 端侧工业违规检测终端

15 天初赛目标：
- GD32H7 作为主控和核心推理端。
- HLK-LD2410 毫米波雷达负责有人进入区域的低功耗触发。
- OV5640/OV2640 摄像头采集低分辨率图像。
- GD32H7 端侧运行轻量二分类或简单检测模型，判断安全/违规。
- 本地声光报警或继电器联动。
- GD32VW553 只上传结构化 JSON 告警，不上传视频流。
- 答辩演示用抓包证明网络中只有几十字节告警数据。

初赛不要做：
- 不做复杂 YOLO 检测。
- 不做多类违规识别。
- 不做音频模型主线。
- 不做 FPGA 主线。
- 不让电脑或手机承担核心推理。

## 两人分工

### A：嵌入式与硬件负责人

核心责任：
- 跑通 GD32H7 工具链、烧录、串口日志。
- 跑通摄像头 DCMI 采集和低分辨率图像缓存。
- 跑通毫米波雷达 UART/GPIO 触发。
- 跑通声光报警、继电器、OLED 或串口状态输出。
- 跑通 H7 与 VW553 的 UART/SPI 通信。
- 集成模型 C 数组或推理库到固件。

交付物：
- 可稳定运行的固件。
- 串口日志格式。
- 端侧推理耗时、RAM/Flash 占用、连续运行测试数据。

### B：算法、数据与展示负责人

核心责任：
- 设计可控演示场景和标注规则。
- 采集并整理安全/违规图片数据。
- 训练轻量二分类模型或传统 ML 基线。
- 完成 INT8 量化、导出 C 数组或可嵌入模型格式。
- 搭建 MQTT/Web/上位机展示页面。
- 准备论文、PPT、演示视频脚本和抓包演示材料。

交付物：
- 数据集说明。
- 模型训练脚本和评估结果。
- 初赛论文/PPT 关键图表。
- 展示端和 Wireshark 抓包截图。

## 15 天推进节奏

### Day 1：硬件与环境冻结

A：
- 确认 GD32H7 板卡型号、下载器、供电方式。
- 跑通 Blink、串口打印、定时器。
- 确认摄像头、雷达、报警器、电源模块是否到货。

B：
- 冻结违规检测目标，建议优先做“危险区域闯入”或“戴帽/未戴帽”二分类。
- 画演示场景草图：摄像头位置、危险区边界、人员站位。
- 准备 PC 端训练环境和数据目录结构。

卡点：
- 板卡不到货：立刻用电脑训练和模拟串口 JSON 展示先推进。
- 工具链装不上：当天必须解决，不允许拖到 Day 2 之后。

### Day 2-3：传感器链路与数据采集

A：
- 跑通毫米波雷达数据读取或 GPIO 触发。
- 跑通摄像头采集，先不追求高帧率，能拿到稳定帧即可。
- 把一帧图像通过串口、SD 卡或调试方式导出给 B 验证。

B：
- 采集第一版数据：每类至少 100-200 张，背景固定、角度固定。
- 先用 PC 端模型跑通安全/违规分类。
- 产出第一版测试集和混淆矩阵。

卡点：
- DCMI 摄像头驱动不稳定：先降分辨率、降帧率，只做单帧触发采集。
- 数据不够：用固定机位和固定场景快速扩充，不要追求真实工厂泛化。

### Day 4-5：模型基线

A：
- 完成图像预处理接口：灰度化、裁剪、缩放到 96x96 或 128x128。
- 准备模型输入缓冲区和推理调用接口。

B：
- 训练两个基线：
  - 传统基线：HOG/SVM 或颜色/边缘/区域特征 + 轻量分类器。
  - 神经网络基线：MobileNetV2 0.25x/0.35x、MCUNet 或更小 CNN。
- 选择更容易部署的一版，不追求最高准确率。

卡点：
- 模型太大：马上缩小输入尺寸和通道数，必要时退回传统 ML。
- PC 准确率不稳定：说明场景定义不清，先收窄到固定相机和固定距离。

### Day 6-8：端侧部署

A：
- 集成 TFLite Micro、NNoM、CMSIS-NN 或导出的纯 C 推理代码。
- 打印每次推理耗时、置信度、模型输出。
- 端侧输出 `safe/violation/confidence`。

B：
- 协助做 INT8 量化和模型格式转换。
- 对比 PC 输出和端侧输出是否一致。
- 记录端侧精度损失和延迟。

卡点：
- 推理库移植失败：优先使用最小纯 C 模型或传统 ML，不要死磕框架。
- RAM 爆掉：减少输入尺寸、减少通道、复用 buffer，关掉不必要 UI。
- 推理太慢：从连续推理改为“雷达触发后 3-5 秒采样数帧投票”。

### Day 9-10：联动闭环

A：
- 雷达触发后唤醒摄像头采集。
- 推理为违规后触发声光报警和继电器。
- H7 通过 UART/SPI 向 VW553 发送告警 JSON。

B：
- 搭建 MQTT/Web/串口上位机展示。
- 准备 Wireshark 抓包脚本和截图模板。
- 设计演示流程：进入区域、报警、上传 JSON、抓包证明无视频流。

卡点：
- VW553 联网耗时长：初赛可以先用串口上位机模拟云端，但必须说明 VW553 是结构化通信链路。
- MQTT 不稳定：用局域网 TCP/UDP 或串口日志作为保底展示。

### Day 11-12：稳定性与指标

A：
- 连续运行 30-60 分钟，记录崩溃、误报、漏报。
- 记录推理耗时、触发到报警延迟、JSON 包大小。
- 记录功耗变化：雷达待机、H7 推理、报警输出。

B：
- 补测试集，整理准确率、召回率、误报率。
- 画系统框图、数据流图、通信协议图。
- 整理与普通摄像头监控方案的对比：隐私、带宽、低延迟、断网可用。

卡点：
- 准确率不够：不要扩大任务，改成更受控的演示条件，并诚实说明适用边界。
- 误报多：用雷达触发 + 多帧投票 + 置信度阈值三层过滤。

### Day 13-14：材料冻结

A：
- 固件冻结，只修 bug，不再加新功能。
- 准备演示备用流程：无 Wi-Fi、无 MQTT、摄像头失效时的降级展示。

B：
- 完成论文初稿、PPT、演示视频。
- 准备答辩讲法：为什么是 Endpoint AI，为什么不传视频，为什么 GD32H7 是核心。

卡点：
- 临时想加功能：拒绝。只加能提升演示稳定性的修复。
- 视频录制翻车：提前录多版，包括正常演示和抓包特写。

### Day 15：提交检查

共同完成：
- 检查论文、PPT、视频、代码说明、硬件照片。
- 检查是否突出兆易芯片、端侧 AI、边缘隐私、低功耗触发。
- 准备 3 分钟、5 分钟、8 分钟三个答辩版本。

## 最高风险卡点排序

1. 摄像头 DCMI 不稳定
   - 现象：花屏、帧丢失、DMA 错乱、内存越界。
   - 对策：单帧采集优先；降分辨率；先不要做实时视频流。

2. 模型无法塞进 MCU
   - 现象：RAM/Flash 不够，推理库编译不过。
   - 对策：输入 96x96；INT8；小 CNN；必要时退回 HOG/SVM。

3. 任务定义太大
   - 现象：想同时做安全帽、闯入、呼救、设备异响。
   - 对策：初赛只做一个主违规，其他写成决赛扩展。

4. VW553 联网链路拖慢进度
   - 现象：Wi-Fi、MQTT、证书、路由器环境不稳定。
   - 对策：先打通 H7 输出 JSON；联网作为展示增强，串口上位机保底。

5. Demo 场景不可控
   - 现象：光照、角度、背景变化导致识别抖动。
   - 对策：固定机位、固定危险区、固定补光；多帧投票。

6. 论文叙事像普通摄像头
   - 现象：评委觉得只是一个低配监控。
   - 对策：强调本地推理、不上传视频、断网可用、低功耗唤醒、结构化告警。

## 最小可过线版本

若时间非常紧，最低版本必须保住这些：
- GD32H7 端侧完成一个真实推理或传统 ML 分类。
- 雷达或按键触发采集。
- 本地声光报警。
- 输出结构化 JSON。
- 展示网络/串口中没有视频流。
- 有测试报告：准确率、延迟、包大小、稳定性。

## 决赛扩展路线

- FPGA 做图像前处理：灰度化、缩放、ROI 裁剪、帧差、Sobel/HOG。
- FPGA 做音频/振动特征：FFT、滤波、滑窗统计。
- 外部 NPU 做高分辨率 YOLO 或轻量 VLM。
- 多节点部署：多个 EdgeCare 节点通过 VW553 上传结构化事件。
- 后台生成巡检日志，但核心隐私数据仍不离开本地。
